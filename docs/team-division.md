# חלוקת עבודה אנכית לצוות

המטרה היא שכל חבר יהיה בעלים של אזור מוצר שלם מקצה לקצה. בעלות על אזור
כוללת את מסך ה-EJS, קוד ה-Vanilla JavaScript וה-AJAX, ה-routes, ה-controllers,
המודלים או השירותים הדרושים, validation, טיפול בשגיאות, בדיקות ותיעוד.

## חלוקת אזורים

| חבר/ה | אזור מוצר מלא | מה נכנס לבעלות |
| --- | --- | --- |
| איתי | Editor Control Room | תור אישורים, עריכת כתבה, אישור/פרסום, החזרה לתיקונים, מחיקה, השוואת גרסאות וכללי workflow |
| חיים | Reporter Workspace | יצירת כתבה, עריכת טיוטה, שמירה אוטומטית, שליחה לאישור, תיקונים ועריכת כתבה שפורסמה |
| דור | Public News Experience | עמוד הבית, פיד, חיפוש, סינון, מיון, infinite scroll, עמוד כתבה, SEO ונגישות |
| ברמר | Identity and Access | Login, logout, sessions אחרי Restart, roles, הרשאות, redirects והגנת routes בצד השרת |
| לירי | Engagement and Insights | תגובות והגבלת ספאם, view events, Impact Analytics ב-Chart.js, weather widget ו-cache |

## מה כל בעלים חייב למסור

כל אזור נחשב גמור רק כאשר קיימים בו:

1. מסך עובד בממשק.
2. API או route מתאים בצד השרת.
3. שמירה ושליפה ממסד הנתונים כאשר נדרש.
4. בדיקות של הצלחה, קלט שגוי והרשאה חסרה.
5. הודעות שגיאה ברורות למשתמש ולוגים בצד השרת.
6. תיעוד קצר באנגלית פשוטה של הקוד והחלטות האזור.
7. תרחיש הדגמה שאפשר להציג בהגנה.

## גבולות בין האזורים

- ברמר הוא הבעלים של `User`, `Session` ו-auth middleware. שאר האזורים
  משתמשים בהם דרך interface קבוע ולא משנים אותם בלי תיאום.
- חיים הוא הבעלים של מבנה תוכן הכתבה הניתנת לעריכה.
- איתי הוא הבעלים של חוקי האישור, הפרסום, ה-revision והגרסה הציבורית.
- דור מציג לציבור רק `publishedVersion` ואינו עורך תוכן במסד הנתונים.
- לירי הוא הבעלים של `Comment`, `ViewEvent`, weather service וגרף האנליטיקות.
- קבצים משותפים כמו `src/app.js` ו-README משתנים רק דרך PR מתואם.

## סדר תלות מומלץ

1. איתי מנסח עם כולם את חוזי ה-API ואת מצבי הכתבה.
2. ברמר משלים login, sessions והרשאות בסיסיות.
3. חיים משלים את אזור הכתב ואת שמירת הכתבות.
4. איתי משלים את אזור העורך ואת מעברי ה-workflow.
5. דור מחבר את התוכן המאושר לפיד הציבורי ולעמוד הכתבה.
6. לירי מוסיף תגובות, צפיות, גרף ומזג אוויר.
7. כל חבר בודק אזור של חבר אחר לפני ההגשה.

## כלל למניעת חפיפות

אין לבצע שינוי ישיר באזור של חבר אחר. אם נדרש שינוי ב-interface משותף,
פותחים issue קטן, מתאמים את החוזה, ואז מבצעים PR ממוקד. בעל האזור מאשר
שהשינוי לא שובר את ה-flow שלו.
